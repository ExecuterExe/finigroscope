# Задание: свести ФинИгроСкоп и «Генератор игр» в один репозиторий

Документ самодостаточный: исполнителю не нужно ничего знать о прошлых
обсуждениях. Читать целиком до начала работы — часть ловушек становится видна
только вместе.

---

## 1. Что делаем и чего НЕ делаем

**Делаем.** Два самостоятельных сервиса кладём в один репозиторий, каждый в свою
папку, со своим окружением и своей точкой входа. Ставим их на один VPS за одним
nginx. Добавляем кнопку перехода между сервисами. Готовим почву для единого
входа.

**Не делаем.**

- **Не сливаем в один процесс.** ФинИгроСкоп — Flask 3 + SQLAlchemy + SQLite.
  Генератор — голый `http.server.ThreadingHTTPServer` со своим обработчиком
  запросов и раздачей статики по белому списку расширений. Чтобы получился один
  сервер, генератор пришлось бы переписать целиком. Смысла сейчас нет.
- **Не сливаем зависимости, конфиги и `.env` в корень.** Почему — раздел 6.
- **Не трогаем внутреннюю логику ни одного из сервисов.** Задание про
  расположение файлов и развёртывание, а не про код агентов.

Если по ходу работы обнаружится, что задание расходится с кодом, — **следовать
коду и сказать об этом**, а не чинить молча.

## 4. Порядок работ

### Шаг 0. Подготовка

1. **Закоммитить всё, что сейчас в работе у ФинИгроСкопа.** Переезд перепишет
   пути у всех файлов сразу; мешать это с содержательными правками в одном

2. Сделать копию обеих папок в стороне (обычным копированием). Это дешевле

3. Убедиться, что тесты ФинИгроСкопа сейчас зелёные — иначе после переезда не
   отличить «сломал переездом» от «было сломано до».

```powershell
cd D:\Работа\python\ФинИгроСкоп
python tests\jobs_check.py
```

### Шаг 1. Создать корень репозитория

Репозиторием становится **существующий репозиторий ФинИгроСкопа** — так
сохранится вся история. Папка проекта превращается в корень экосистемы, а сам
проект уезжает на уровень вниз.

```powershell
cd D:\Работа\python\ФинИгроСкоп
New-Item -ItemType Directory -Force finigroskop

# всё, кроме .git и новой папки, переносим внутрь
Get-ChildItem -Force | Where-Object { $_.Name -notin @('.git', 'finigroskop') } |
    ForEach-Object { Move-Item -LiteralPath $_.FullName -Destination finigroskop }

git add -A
git status          # убедиться, что git распознал переименования (R), а не удаления
```

Git определяет переименования по содержимому, поэтому история файлов
сохраняется и после `Move-Item`. Если в `git status` видны сплошные
`deleted`/`new file` — это нормально до `git add -A`; проверять надо **после**.

Папку `.claude` при этом тоже уносим внутрь — на шаге 3 она вернётся в корень
объединённой.

### Шаг 2. Внести генератор

```powershell
cd D:\Работа\python\ФинИгроСкоп        # это уже корень экосистемы
Copy-Item -Recurse D:\Работа\python\Generation_games generator

# мусор, который в репозиторий не нужен
Remove-Item -Recurse -Force generator\__pycache__, generator\.pytest_cache -ErrorAction SilentlyContinue
Remove-Item -Recurse -Force generator\logs -ErrorAction SilentlyContinue
```

**`generator\.env` не коммитить никогда** — в нём настоящий ключ OpenRouter. Он
уже закрыт `.gitignore` внутри папки генератора; после переноса проверить, что
закрыт по-прежнему:

```powershell
git check-ignore -v generator\.env finigroskop\.env
```

Обе строки должны что-то вывести. Если хоть одна молчит — **остановиться** и
чинить `.gitignore`, прежде чем делать `git add`.

Папку `generator\.claude` разобрать по шагу 3 и удалить.

Переименовать корневую папку с диска (`ФинИгроСкоп` → `Экосистема` или как
решите) — операция на файловой системе, git её не заметит.

### Шаг 3. Корневые файлы

**`.gitignore` в корне** — короткий. Подробные списки остаются внутри каждого
подпроекта, git читает вложенные `.gitignore` сам:

```gitignore
# Общее для всей экосистемы. Частности — в .gitignore каждого подпроекта.
__pycache__/
*.py[cod]
.venv/
venv/
.idea/
.vscode/
.claude/settings.local.json
```

**`.claude/launch.json`** — обе конфигурации в одном файле:

```json
{
  "version": "0.0.1",
  "configurations": [
    {
      "name": "finigroskop",
      "runtimeExecutable": "python",
      "runtimeArgs": ["finigroskop/app.py"],
      "port": 5000
    },
    {
      "name": "generator",
      "runtimeExecutable": "python",
      "runtimeArgs": ["generator/app.py"],
      "port": 8000
    }
  ]
}
```

Так работает потому, что оба сервиса считают свои пути от `__file__`, а не от
текущего каталога: `config.py` ФинИгроСкопа и `app.py` генератора оба используют
каталог собственного файла. Запуск из корня им не мешает.

**`.claude/settings.json`** — объединить запреты и **добавить недостающий для
ФинИгроСкопа** (сейчас его `.env` ничем не защищён):

```json
{
  "permissions": {
    "deny": [
      "Read(./generator/.env)",
      "Read(./finigroskop/.env)",
      "Bash(cat:*.env)",
      "Bash(type:*.env)"
    ]
  }
}
```

**`README.md` в корне** — что где лежит, как поднять каждый сервис, куда смотреть
дальше. Обязательно указать: **тесты ФинИгроСкопа запускаются из папки
`finigroskop/`, тесты генератора — из `generator/`** (почему — раздел 6).

### Шаг 5. Кнопка перехода между сервисами

### Шаг 6. deploy/

Два systemd-юнита и один конфиг nginx.

**`deploy/systemd/finigroskop.service`**

```ini
[Unit]
Description=ФинИгроСкоп
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/srv/ecosystem/finigroskop
EnvironmentFile=/srv/ecosystem/finigroskop/.env
# ОДИН воркер. Очередь фоновых задач живёт ВНУТРИ процесса: при нескольких
# воркерах у каждого будет своя, и статус задачи придёт не от того процесса,
# который её считает. Больше одного воркера — только вместе с настоящей очередью.
ExecStart=/srv/ecosystem/.venv/bin/gunicorn -w 1 -b 127.0.0.1:5000 --timeout 900 app:app
Restart=always

[Install]
WantedBy=multi-user.target
```

**`deploy/systemd/generator.service`**

```ini
[Unit]
Description=Генератор игр
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/srv/ecosystem/generator
# gunicorn здесь НЕ подходит: сервер генератора не WSGI-приложение, а
# собственный обработчик http.server. Запускается как есть.
ExecStart=/srv/ecosystem/.venv/bin/python app.py
Restart=always

[Install]
WantedBy=multi-user.target
```

**`deploy/nginx/ecosystem.conf`**

```nginx
server {
    listen 80;
    server_name ВАШ-ДОМЕН;

    # --- ФинИгроСкоп: корень ---
    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 32m;          # загрузка .docx
    }

    # --- Генератор игр ---
    location /generator/ {
        proxy_pass http://127.0.0.1:8000/;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # Генерация идёт синхронно и занимает до минуты — короткий таймаут
        # оборвёт запрос ровно тогда, когда модель уже начала отвечать.
        proxy_read_timeout 300s;
    }
}
```

**Важно про подключение генератора по пути `/generator/`.** Его страница зовёт
свой сервер по АБСОЛЮТНЫМ адресам — `app.js`, строки 1039 и 1215:
`fetch('/api/generate/mechanics')` и `fetch('/api/audit/mechanics')`. Из-под
префикса `/generator/` такой запрос уйдёт в корень домена, то есть **в
ФинИгроСкоп**, и вернётся 404. Два выхода:

- **Проще и надёжнее — поддомен:** `generator.ваш-домен` отдельным `server`-блоком
  с `proxy_pass http://127.0.0.1:8000;` и `location /`. Тогда в коде страницы
  менять нечего.
- **Либо путь:** заменить в `app.js` оба абсолютных адреса на относительные
  (`'api/generate/mechanics'`), проверить, что в файле не осталось других
  строк, начинающихся с `/api/`, и что страница открывается именно по адресу с
  завершающим слэшем (`/generator/`, не `/generator`) — иначе относительный путь
  соберётся неверно.

Выбор зависит от того, будет ли общий вход (раздел 7): для куки поддомен —
отдельный домен, и куку придётся выдавать на `.ваш-домен`. Если общий вход
планируется, **берите путь, а не поддомен.**

### Шаг 7. Единый вход (отдельный этап, можно позже)

У генератора нет ни сессий, ни пользователей — добавлять их туда не нужно.
Владельцем пользователей остаётся ФинИгроСкоп: там уже есть модель `User`, роли
и вход по @телеграм-нику с паролем.

Порядок:

1. В ФинИгроСкопе выключить гостевой режим: `AUTH_DISABLED = False` в `app.py`.
   **Учесть:** сейчас на этом флаге завязана логика гостевых пользователей и
   очистка хранилища. Проверить весь набор тестов после переключения — часть
   проверок ходит по страницам без входа.
2. Задать `FINIGROSKOP_SECRET` в `.env` на сервере — длинное случайное значение.
   Без него используется общеизвестное значение по умолчанию, и подделать
   сессию сможет кто угодно.
3. Добавить в ФинИгроСкоп внутренний эндпоинт проверки сессии, например
   `GET /api/whoami`: 200 и `{"tg_tag": …}` для вошедшего, 401 для остальных.
4. Закрыть генератор через `auth_request` — тогда в самом генераторе не
   появляется ни строчки про авторизацию:

```nginx
    location /generator/ {
        auth_request /_auth;
        auth_request_set $user $upstream_http_x_user;
        proxy_set_header X-User $user;
        proxy_pass http://127.0.0.1:8000/;
        # …остальные заголовки как выше…
    }

    location = /_auth {
        internal;
        proxy_pass              http://127.0.0.1:5000/api/whoami;
        proxy_pass_request_body off;
        proxy_set_header        Content-Length "";
        proxy_set_header        X-Original-URI $request_uri;
    }
```

Разбирать подписанную куку Flask силами генератора **не надо** — без Flask это
возня с форматом `itsdangerous`, которая сломается при первом же обновлении
библиотеки.

## 5. Чего делать нельзя (перечитать перед `git commit`)

1. **Один `.env` в корне на оба сервиса.** Имена переменных совпадают, а смысл
   разный:

   | Переменная | ФинИгроСкоп | Генератор |
   |---|---|---|
   | `LLM_PROVIDER` | один из девяти вендоров | принимает только `openrouter`, иначе отказ |
   | `LLM_TIMEOUT` | 25 с | 60 с |
   | модель | `OPENROUTER_MODEL` (одна, необязательна) | `OPENROUTER_MODEL_PRO` / `_FLASH` / `_REASONING` |

   Один файл на двоих молча даст каждому чужие значения. **Два `.env`, по одному
   в каждой папке.**

2. **Не добавлять обе папки в `sys.path` одновременно.** У обоих проектов есть
   модуль верхнего уровня `config`, и это разные модули: генератор делает
   `from config import config` (объект), у ФинИгроСкопа такого объекта нет.
   Победит тот, кто окажется в `sys.path` первым, второй сломается. Пока каждый
   сервис запускается своим `app.py` — всё в порядке: Python сам кладёт в
   `sys.path[0]` каталог запускаемого скрипта.

3. **Не запускать тесты ФинИгроСкопа из корня экосистемы.** Они начинаются с
   `sys.path.insert(0, ".")` и рассчитывают на текущий каталог проекта. Из корня
   импорт `app` не найдётся, а при неудачном стечении — найдётся чужой `config`.
   Запускать только из `finigroskop/`.

4. **Не запускать Alembic из чужого каталога.** В `alembic.ini` стоит
   `prepend_sys_path = .`, то есть в `sys.path` попадает **текущий** каталог.
   Хорошая профилактика: заменить эту строку на `prepend_sys_path = %(here)s` —
   тогда путь считается от самого ini-файла и от каталога запуска не зависит.
   Замену сделать в этом же переезде и прогнать `python tests\jobs_check.py`.

5. **`FINIGROSKOP_RESET` на сервере не задавать никогда.** Эта переменная
   разрешает **стереть хранилище при старте**. В разработке её включает сам
   `python app.py`; на сервере запуск идёт через gunicorn, который её не ставит,
   — но если кто-то пропишет её в `.env`, каждый перезапуск сервиса будет
   уничтожать все документы пользователей.

6. **Больше одного воркера gunicorn — нельзя** без замены очереди задач. Причина
   в юните выше.

7. **Не коммитить `.env` ни одного из сервисов.** В генераторском лежит
   действующий ключ OpenRouter. Если он всё-таки попал в историю — ключ
   считается скомпрометированным, его надо отозвать на
   https://openrouter.ai/keys, а не просто удалить файл следующим коммитом.

8. **Не сливать `logs/` генератора в репозиторий.** Там журнал вызовов модели с
   кусками пользовательских ответов.

## 6. Чек-лист приёмки

Переезд считается выполненным, когда всё ниже — правда:

- [ ] `git status` чист, в истории видны переименования, а не «удалили и создали заново»
- [ ] `git check-ignore -v finigroskop/.env generator/.env` — обе строки закрыты
- [ ] `git log --follow finigroskop/app.py` показывает историю до переезда
- [ ] из `finigroskop/`: все 17 наборов проверок дают `ВСЁ ОК`
- [ ] из `finigroskop/`: `config.database_path()` указывает внутрь `finigroskop/instance/`
- [ ] из `generator/`: `python -m pytest tests -q` зелёный, `python llm.py` отвечает
- [ ] оба сервиса поднимаются одновременно: 5000 и 8000, друг другу не мешают
- [ ] в шапке каждого сервиса есть работающая кнопка перехода во второй
- [ ] адреса переходов берутся из окружения, а не зашиты в шаблон
- [ ] `deploy/` содержит оба юнита и конфиг nginx, в юните ФинИгроСкопа `-w 1`
- [ ] в корне есть README, где сказано, из какой папки что запускать

## 7. Что осознанно оставлено на потом

- **Передача данных между сервисами.** Сгенерированная игра должна попадать в
  агентов ФинИгроСкопа без экранов. Это API-контракт, и он не зависит от
  раскладки файлов. Делать после того, как генератор начнёт выдавать описание
  игры целиком (сейчас у него готовы только механики и аудит модуля).
- **Общий словарь статусов.** У аудитора генератора это
  `ok / concern / violation / n/a`, у стадии понимания игры ФинИгроСкопа —
  `ok / unclear / missing / absent`. Смысл близкий, правило «n/a не равно ok»
  общее. Свести их стоит осознанным решением, а не случайно при интеграции.
- **Журнал вызовов модели.** У генератора есть `runlog.py` и
  `logs/llm_calls.jsonl`; у ФинИгроСкопа сырые ответы модели нигде не
  сохраняются, и это отдельный пункт его собственного плана доработок. Разумно
  сделать один механизм на оба сервиса — но не в этом переезде.
